## 调度与总协调

当前并发能力为主会话加三个代理。下列四种职责通过轮换承接，不要求同时启动四个代理。

1. 取证阶段：需求分析、客户端视觉调查、QA 验收规划并行处理各自文档；浏览器由主会话分配独占时段。
2. 契约阶段：需求分析汇总已证实的首个操作闭环，客户端与服务端提出实现方案，主会话审核渲染选择、数据与接口契约。
3. 实现阶段：客户端、服务端、独立 QA 三个代理协作；发现证据缺口时交回主会话安排补充取证，受影响功能等待核实。
4. 验收阶段：QA 独立执行两层测试，开发代理修复各自缺陷；主会话对照原版范围核验，统一提交并报告真实完成度。

主会话负责目标与范围、角色轮换、文件所有权、浏览器排程、共享契约审核、跨端集成、缺陷分派、Git 提交与上传。只在活动会话中报告监控结果，不宣称会话结束后仍自动工作。

## 任务卡 A：需求分析与原版行为取证

**目标**：形成可实现、可验收的原版行为清单，明确 1:1 对照范围和未知项。

**输入**：附带公共上下文；原版入口与已有证据；主会话分配的浏览器时段；用户确认的目标版本。当前未进服，不具备游戏内完整需求。

**输出与建议文件责任**：维护 `docs/reference-evidence.md`；新增 `docs/gameplay-spec.md` 记录系统清单、页面流转、前置条件、操作前后状态、可见数值及证据编号；新增 `docs/open-questions.md` 记录无法观察的规则与需要补采的证据。验收矩阵交给 QA 更新，不抢写。

**前置依赖**：游戏服务器可进入，并能观察相关功能。锁定或不可访问系统保留未知状态；先整理已取得证据。

**执行边界**：区分直接观察、重复操作验证、推断与未知。观察结果不自动代表内部公式；未经验证不建立概率、成长或经济规则。记录原版版本及初始状态，避免把账号进度差异当产品规则。涉及真实购买等操作交主会话处理，不自行执行。

**完成标准**：每个拟交付功能有唯一编号、证据、可复现操作、预期状态、依赖与未知项；首个闭环足以让前后端及 QA 独立理解；主会话审核后移交。局部调查完成不等于完整游戏范围已确定。

**报告格式**：已核实功能编号与证据路径；新增未知项及影响；可开始实现的范围；仍需浏览器的具体操作；修改文件与交接对象。

## 任务卡 B：客户端、视觉与资源

**目标**：还原已证实的页面、场景、输入、动画及状态反馈，建立可交互客户端。

**输入**：附带公共上下文；任务卡 A 的行为规格；原版截图与操作证据；经主会话审核的渲染方案和前后端契约。

**输出与建议文件责任**：先提交 `docs/client-design.md` 与 `docs/asset-inventory.md`，说明画面层次、视口、动画/资源清单、来源和缺口；实现阶段建议负责 `client/` 及其资源。目录仅为责任建议，现阶段不代表已有项目结构。共享契约变更提交给主会话审核。

**前置依赖**：先核实 2D/3D 表现、角色动作、镜头、遮挡、地图移动和 UI 层级，再确定渲染引擎。Unity WebGL 标志不能独自决定复刻引擎。具体功能需有行为规格及可用接口契约；服务未就绪时的开发模拟须明确标识，不得作为交付完成证据。

**执行边界**：不得以静态图片、CSS 卡片或硬编码成功提示替代已确认的场景动画和操作。资源缺口明确列出；占位素材不计为 1:1 完成。不得把原站客户端嵌入页面充当本地复刻，不保存敏感会话信息，不猜测服务器结果。

**完成标准**：负责范围可运行、可实际点击；状态与已确认服务端结果一致；对照固定视口的原版视觉及动作证据记录差异；交付启动方式、资源清单、功能编号与剩余缺陷，由独立 QA 执行页面及接口交叉验收。

**报告格式**：完成的功能编号；关键视觉对照证据；接口依赖及差异；构建/运行结果；未完成动画或素材；修改文件与 QA 复现步骤。

## 任务卡 C：服务端、数据与测试支付

**目标**：实现已证实的状态变更、持久化和本地测试支付流程，为客户端提供可验证的数据服务。

**输入**：附带公共上下文；任务卡 A 的规则及证据；主会话审核的数据与接口契约；客户端操作流程和 QA 验收要求。

**输出与建议文件责任**：先提交 `docs/server-design.md`，提出数据模型、状态流转与持久化方案；实现阶段建议负责 `server/`、服务端数据迁移及相关接口测试。API 契约文档及共享类型由主会话指定单一责任人维护。

**前置依赖**：具体状态、计算规则、资源增减与奖励必须有已确认依据。测试支付直接成功是用户已确认的本地差异；档位、奖励和权益仍需原版证据。未确定的数据方案不提前写死。

**执行边界**：不得猜测端点、概率、数值、掉落或成长公式。添加校验前查看入口和调用链，遵守既有规则，避免重复校验与无依据兼容逻辑。本地充值不调用原站支付、不产生真实扣款；模拟成功后须按已确认规则持久化订单与奖励，同单重试不得重复发放。

**完成标准**：已确认功能有可重复的接口测试与前后状态证据；持久化要求经过重启读取验证；测试支付有订单、资源变化和重复请求的测试记录；客户端能按契约接入。接口通过不代表整体游戏验收通过。

**报告格式**：实现的功能与契约版本；数据变更与启动步骤；测试命令及结果；订单/奖励验证摘要；客户端接入信息；未知项、缺陷与修改文件。

## 任务卡 D：独立 QA 与完整性核验

**目标**：以原版证据独立验证接口和真实页面操作，指出视觉、交互、规则、状态及持久化差异。

**输入**：附带公共上下文；原版功能和证据清单；当前实现、启动步骤及契约；可重复准备的本地测试数据；主会话分配的内部浏览器时段。

**输出与建议文件责任**：维护 `docs/test-plan.md`、`docs/acceptance-matrix.csv`；建议负责 `tests/` 中独立验收用例及 `docs/qa-report.md`，记录缺陷、复测和证据索引。证据内容须去敏。

**前置依赖**：无实现时只完善验收用例，保持 NOT_RUN；存在明确阻塞时记录 BLOCKED 及恢复条件。执行要求本地服务可运行、范围已确认、测试数据可准备。不能把原版站点的操作通过记为本地实现通过。

**执行边界**：接口调用、修改存档或直接调用内部函数不能替代页面点击。功能同时核验请求前后状态、真实点击结果及页面展示；环境可用不等于游戏功能通过。不得为了让测试通过擅自改变规则、放宽标准或修正原版证据。

**完成标准**：每项已确认功能同时具备接口与页面证据；失败项有复现步骤并经修复后复测；视觉和动作对照列明差异；本地测试支付、刷新与需持久化状态的服务重启流程均按确认要求验证。完整性核验必须披露未调查、未实现、未测试及不可访问范围，不以局部 PASS 宣称完整复刻。

**报告格式**：测试提交/工作区版本和环境；功能编号与 API/UI 各自结果；证据路径；缺陷严重度、复现步骤及责任人建议；复测结果；尚未覆盖范围与最终验收建议。
